# このフォークでのPRの作り方（AIエージェント向け）

このフォーク（Ybrain）のオーナーは、すべてのコードを細かく読む時間がありません。
**オーナーが「コードを読む前に」判断できるように**進めてください。やりとりとPRの説明は日本語で書きます。

このファイルは、CLAUDE.md の末尾の1行から参照されています（CLAUDE.md にはサイズ上限があるため、ルールはこちらに置いています）。

## 1. 実装の前に計画を見せる

コードを書き始める前に、次の4点を短く示して、オーナーの OK を待ってください。

- 何を変えるか
- なぜ変えるか
- どう変えるか
- 検討した他の案と、それを選ばなかった理由

危険度が「高」の変更では、計画の段階で「元に戻せるかどうか」も書いてください。
「高」に当たる場所は `.github/copilot-instructions.md` の「このリポジトリで危険度「高」とする場所」を参照してください。

## 2. PRは小さく

- 1つのPRで目的は1つにする
- 関係のないリファクタリングや整形を混ぜない
- 大きくなりそうなら、先に分け方を提案する

## 3. PRの説明を必ず埋める

`.github/PULL_REQUEST_TEMPLATE.md`（日本語）の項目をすべて埋めてください。特に次の2つは省略しないでください。

- 「レビュアーに判断してほしいこと」: はい／いいえで答えられる質問にする
- 「戻し方」

本家（garrytan/gbrain）に送るPRだけは、英語のテンプレート `.github/PULL_REQUEST_TEMPLATE/upstream.md` と、CLAUDE.md の本家向けルール（タイトルの書き方など）に従ってください。

## 4. やってはいけないこと

- テストを消す、スキップする、期待値を実装に合わせて書き換えるだけで通す
- 秘密情報（APIキー、パスワード、トークン）をコードやログに書く
- オーナーの OK なしに、元に戻せないデータ操作を含める

## 5. オーナーの理解チェックを手伝う

オーナーが「このPRを自分の言葉で説明するので添削して」と頼んだら、次の順で答えてください。

1. オーナーの説明のうち、合っている点
2. 間違っている点・抜けている点（実際の差分のどこに書かれているかを示す）
3. 判断の前に確かめるべきこと（あれば）

答えを先に全部言わず、まずオーナーの説明を待ってください。
